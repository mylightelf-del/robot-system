# 19. 안드로이드 앱 설계 — 의논용 초안 (2026-11-07)

사용자 요청: "웹서비스를 어느 정도 개발했는데 앱으로도 구현하고 싶다. 안드로이드부터 시작. 의논하면서 설계부터."
이 문서는 **결정 전 초안**이다. 9장의 결정 항목이 정해지면 그에 맞춰 고치고, 구현은 그 뒤에 시작한다. 코드 변경은 아직 없다.

## 0. 먼저 솔직하게 — 앱이 무엇을 더 주는가
현재 웹(`docs/18` A5)은 이미 폰 브라우저에서 "홈 화면에 추가"로 앱처럼 열리고(PWA), 390px 폭 화면 점검도 끝났다. 그래서 "앱을 만든다"가 실제로 채우는 빈칸을 분명히 하고 시작한다.

| 지금 웹(PWA)에 없는 것 | 앱으로 얻는가 | 비고 |
|---|---|---|
| **푸시 알림**(장애·미실행·보고서를 폰 알림창으로) | ○ 가장 큰 이유 | 지금은 이메일·카카오톡 '나에게 보내기'뿐. 현장 담당자가 장애를 **즉시** 아는 길이 없다 |
| 스토어 배포(고객사에 "앱 깔아 주세요"라고 안내) | ○ | 고객사 입장에서 신뢰감. 내부 직원만이면 APK 직접 설치로도 충분 |
| 생체인증(지문/얼굴)으로 빠른 로그인 | ○ | 웹 세션은 12시간 유휴 만료라 현장에서 자주 다시 로그인 |
| 카메라로 장애 조치 사진 바로 첨부 | ○ | 웹에서도 `<input type=file>`로 되지만 앱이 매끄럽다 |
| 오프라인에서 마지막 상태 보기 | △ | 관제는 최신 값이 중요해 효용은 작다 |
| 제조사 앱(PUDU Link)과 같은 수 초 실시간 | × | 앱을 만들어도 데이터는 같은 서버·같은 PUDU 폴링(60초)/콜백에서 온다. 앱이 빨라지는 것이 아니다 |

**대안도 적어 둔다**: 푸시만 급하면 지금 PWA에 **Web Push**(브라우저 푸시, 안드로이드 Chrome·iOS 16.4+ 홈화면 추가 시 지원)를 붙이는 쪽이 며칠 일이고 스토어가 필요 없다. 그래도 앱을 만들 이유는 위 표의 2~4행과 **다음에 iOS까지** 가는 길이다. 아래 설계는 앱을 만든다는 전제로 쓰되, 0단계(서버 API)는 Web Push를 택해도 대부분 그대로 쓰인다.

## 1. 앱의 범위 — 무엇을 앱에 넣고 무엇을 웹에 남기나
원칙: **앱은 "현장에서 폰으로 하는 일"만**, 설정·편집·문서 작업은 웹에 남긴다. 두 군데서 같은 화면을 유지하는 비용을 줄인다.

| 구분 | 앱(1차) | 웹에 남김(앱에서는 링크로 열기) |
|---|---|---|
| 조회 | 홈(오늘 할 일·사업장별 현황), 사업장 관제(층 지도·로봇 위치), 로봇 상세(상태·배터리·소모품·최근 작업), 장애 목록·상세, 보고서 **확정·공개본** 목록과 PDF 보기 | 작업·일정 상세표, 감사 기록, 고급 설정, 보고서 초안·수치 보정·PPT·Excel |
| 조작 | 장애 **확인·담당자 지정·조치 등록·복구**, 로봇 명령(시작·일시정지·재개·중지·복귀 — 웹과 같은 조건: 사업장 원격 제어 스위치·명령 권한·상태 신선도), 알림 읽음 | 사용자·사업장·층·로봇 등록, 수신자 설정, 제조사 연동, 사용 중지 |
| 내 계정 | 푸시 켜기/끄기, **내 알림 구독**(이미 있는 기능 재사용), 로그인된 기기 목록·끊기, 생체인증 잠금(2차) | 비밀번호 변경, 카카오 연결 |

역할별 차이는 웹과 **동일**하다(서버가 검사). 고객 기본 계정은 조회·확정 보고서만, 고객 제어는 허용된 명령만, 고객에게 원시 오류·내부 메모·초안을 보내지 않는다(`sanitizeIncident`·`toRobotView` 그대로 사용).

1차 대상 사용자 제안: **현장 담당자 → 본사 → 고객사** 순. 현장 담당자가 푸시를 받고 장애를 처리하는 흐름이 가장 효용이 크다.

## 2. 구조 — 서버에 무엇을 더해야 하나
현재 웹은 Next.js 서버 컴포넌트 + 서버 액션(`src/app/actions.ts`)으로 동작한다. 즉 **앱이 호출할 수 있는 JSON API가 사실상 없다**(`/api/health`, 지도 이미지, 보고서 내보내기, 콜백뿐). 다행히 업무 규칙은 `src/lib/services/*`에 `user`를 첫 인자로 받는 함수로 분리돼 있어, 그 위에 얇은 JSON 라우트를 얹으면 된다. 업무 규칙·권한 검사 코드는 **복제하지 않는다**.

```
폰 앱 ──HTTPS(JSON, Bearer 토큰)──▶ widebot.kro.kr/api/v1/*  ──▶ src/lib/services/* (웹과 같은 함수)
  ▲                                                                   │
  └──── FCM 푸시 ◀── worker(알림 모듈에 PUSH 채널 추가) ◀──────────────┘
```

### 2.1 인증 — 토큰
- 웹 쿠키 세션(`sessions` 테이블, 유휴 12시간·절대 30일)을 그대로 쓰되 **앱용 세션은 길게**(제안: 유휴 30일·절대 180일). 토큰은 쿠키 대신 `Authorization: Bearer <토큰>` 헤더로 보낸다.
- `sessions`에 `kind`(web/mobile)·`deviceName`·`pushDeviceId` 열 추가 → 내 계정에서 "로그인된 기기" 목록과 개별 끊기, 사용자 비활성화 시 즉시 차단(지금 로직 그대로: 매 요청 사용자 상태 확인).
- 토큰은 DB에 **해시로 저장**(지금 웹 세션 ID는 원문 저장 — 앱 토큰부터 해시로 하고, 웹도 같이 바꿀지는 별도 결정).
- 로그인 실패 잠금·감사 기록은 기존 `services/auth.login` 재사용. 앱 로그인 화면에서도 실패 사유를 구분해 보여 주지 않는다.
- 앱에서 토큰 보관: 안드로이드 Keystore 기반 암호 저장소(EncryptedSharedPreferences / `expo-secure-store`). 평문 파일·로그에 남기지 않는다.

### 2.2 JSON API(`/api/v1`) — 1차 목록
모두 기존 서비스 함수를 그대로 호출한다. 응답 모양은 서비스가 돌려주는 타입(`DashboardData`, `RobotRow`, `IncidentView` 등)을 그대로 JSON으로.

| 메서드·경로 | 서비스 함수 | 비고 |
|---|---|---|
| POST `/auth/login` | `auth.login` | 본문 email·password·deviceName → 토큰·사용자 |
| POST `/auth/logout` | `auth.logout` | 그 기기 토큰만 |
| GET `/me` | 세션 | 역할·사업장 권한·명령 권한 |
| GET `/dashboard`, GET `/todo` | `dashboard.getDashboard/getTodo` | 홈 |
| GET `/sites`, GET `/sites/{id}?floorId=` | `robots.listSites/getSiteView` | 층 지도·로봇 위치 |
| GET `/maps/{mapVersionId}` | 기존 라우트 | Bearer 도 받도록 수정 |
| GET `/robots?siteId=`, GET `/robots/{id}` | `robots.listRobots/getRobotDetail` | |
| POST `/robots/{id}/commands` | `commands.issueCommand` | **멱등 키** 필수(같은 버튼 중복 탭 방지, `docs/HANDOFF` 9장 필수 시험) |
| GET `/commands?robotId=` | `commands.listCommands` | 명령 결과 추적(접수≠완료) |
| GET `/incidents?siteId=&includeResolved=` | `incidents.listIncidents` | |
| POST `/incidents/{id}/ack · assign · actions · resolve` | 같은 이름의 함수 | 되돌리기·삭제는 웹에만 |
| GET `/reports?siteId=`, GET `/reports/{id}/export?format=pdf` | `reports.*`, 기존 내보내기 | 고객은 확정·공개본만(기존 규칙) |
| POST/DELETE `/devices` | 신규 | FCM 토큰 등록·해제 |
| GET/POST/PATCH/DELETE `/subscriptions` | `notify.subscribeMe` 등 | 내 알림 구독 재사용 |
| GET `/notifications?since=` | `notification_logs` | 앱 알림함(내게 온 것만) |

공통 규칙: 오류는 `{ error: { code, message } }`(기존 `AppError.code` 그대로), 시간은 ISO UTC + 사업장 시간대 문자열, 목록은 `limit`·`cursor`. 앱은 화면이 켜져 있을 때 **30초 주기 갱신**(웹 `AutoRefresh`와 같은 역할), 이벤트는 푸시로 받는다.

### 2.3 푸시 — FCM(Firebase Cloud Messaging)
- 안드로이드 푸시의 표준 경로. 서버(worker)는 Firebase Admin SDK(HTTP v1)로 보낸다. **Firebase 프로젝트는 사용자 Google 계정으로 만든다**(AWS 리전 제약과 무관). 서비스 계정 키는 서버 `.env`(또는 마운트 파일)에만 두고, 앱의 `google-services.json`은 비밀값이 아니다(앱에 포함돼야 한다).
- 데이터 모델: `push_devices`(id, userId, fcmToken, platform, appVersion, lastSeenAt, disabledAt). 토큰은 사용자당 여러 개(폰 교체).
- **알림 모듈에 채널 하나 추가**: `notification_recipients.channel`에 `PUSH`, 주소는 카카오와 같은 `user:<사용자ID>`. 그러면 기존의 통보 종류(kinds)·등급·시간대·중복 억제·발송 기록(`notification_logs`)·내 알림 구독 화면이 **그대로** 적용된다. 새 규칙을 만들지 않는다.
- 내용: 알림창에는 제목·한 줄 요약만(예: "선릉센터 · 1호기 · 장애 발생"), 본문은 앱이 열려서 서버에서 다시 받는다 → 고객 계정에 원시 오류 문구가 알림창으로 새지 않는다. 데이터에 `kind·refId·siteId`를 실어 **딥링크**(장애 상세로 바로).
- 실패 처리: FCM이 "토큰 무효"를 돌려주면 그 기기를 비활성 처리. 발송 결과는 기존 `SENT/FAILED`로 기록.

### 2.4 서버에서 바꾸지 않는 것
권한 규칙(`authz.ts`), 명령 안전장치(사업장 스위치·신선도·중복 방지), 고객 비노출 규칙, 감사 기록, DB 구조의 핵심. 앱은 **새 입구**일 뿐이다.

## 3. 앱 화면(1차)
```
로그인 ─▶ 홈(오늘 할 일 카드 · 사업장별 카드 · 7일 KPI 한 줄)
          ├─ 사업장 ─▶ 층 선택 · 지도 위 로봇 위치 · 로봇 목록
          │            └─ 로봇 상세 ─▶ 상태·배터리·소모품·최근 작업·장애 / [명령] 시트(확인 대화상자·사유)
          ├─ 장애 ─▶ 목록(미조치 우선, 사업장·등급 필터) ─▶ 상세(타임라인 · 확인/담당/조치/복구 버튼)
          ├─ 보고서 ─▶ 확정·공개본 목록 ─▶ PDF 보기 · 공유
          ├─ 알림함 ─▶ 내게 온 통보(푸시·이메일·카카오 공통 기록) ─▶ 해당 화면으로
          └─ 내 계정 ─▶ 푸시 켜기 · 내 알림 구독 · 로그인된 기기 · (2차) 생체인증 잠금 · 웹으로 열기
```
- 하단 탭 5개: 홈 · 사업장 · 장애 · 보고서 · 내 계정. 알림함은 홈 상단 종 아이콘.
- 샘플/시뮬레이션 모드 띠, 상태 색+아이콘+글자 병용, 한국어 우선 — 웹과 같은 규칙(`docs/HANDOFF` 2장).
- 명령 버튼은 웹과 같은 조건에서만 보이고, 누르면 **확인 대화상자 → 전송 → "접수됨(실행 확인 중)" → 상태로 확인**까지 보여 준다. HTTP 성공을 완료로 표시하지 않는다.

## 4. 기술 선택 — 후보 비교
| 후보 | 장점 | 단점 | 이 프로젝트에서 |
|---|---|---|---|
| **A. Kotlin + Jetpack Compose(네이티브)** | 안드로이드 표준. 성능·플랫폼 기능(알림 채널·백그라운드)에 가장 자유로움. 구글 문서가 전부 이 기준 | 새 언어·새 생태계. iOS는 처음부터 다시(또는 KMP로 공유 레이어 설계 필요). 빌드가 무겁다 | "안드로이드 전용, 제대로"면 이것 |
| **B. Expo(React Native, TypeScript)** | 서버와 **같은 언어(TypeScript)·같은 타입**을 공유(`src/lib/domain/types.ts`를 그대로 import 가능). iOS가 같은 코드. 클라우드 빌드(EAS)로 Android Studio 없이 가능. 푸시·보안 저장소·카메라 모듈이 준비돼 있다 | 네이티브보다 한 겹 두꺼움. 네이티브 모듈이 필요할 때 난이도 상승(이 앱은 목록·카드·이미지 지도·폼 위주라 해당 없음) | **추천**. 사용자가 Claude와 함께 TypeScript 저장소를 이미 운영 중 |
| C. Flutter(Dart) | 성숙한 크로스플랫폼, UI 일관성 | Dart는 또 다른 언어. 타입 공유 안 됨 | 장점이 B를 넘지 않음 |
| D. TWA/WebView 껍데기 + FCM | 가장 빠름(며칠). 화면은 전부 지금 웹 | "앱"이라기보다 웹 바로가기. 푸시 외 이점 거의 없음. 스토어 심사에서 저품질 판정 가능 | 0장의 Web Push와 사실상 같은 급 — 그렇다면 Web Push가 더 간단 |

**추천: B(Expo)**. 근거: ① 다음 단계가 iOS일 가능성이 높다고 사용자가 말했다("안드로이드부터"). ② 서버·앱이 한 저장소·한 언어면 타입 불일치 사고가 줄고 Claude 세션이 양쪽을 한 번에 고친다. ③ 이 컨테이너에는 Android Studio·에뮬레이터가 없다. Expo는 클라우드 빌드 또는 `expo prebuild` + Gradle로 여기서도 APK를 만들 수 있다(확인: JDK 21·Gradle 8.14 설치됨, `dl.google.com`·Maven·`api.expo.dev` 접근 가능 — SDK는 설치 필요). A를 고르면 추천을 철회하지 않고 A로 간다. 그 경우 2장의 서버 작업은 동일하다.

## 5. 저장소 구성(제안)
```
robot-system/
  src/            (지금 그대로: 웹 + API 라우트 + worker)
  src/app/api/v1/ (신규: 앱용 JSON 라우트)
  mobile/         (신규: Expo 앱. 자체 package.json. 서버 타입은 상대 경로로 import)
  docs/19-...     (이 문서)
```
한 저장소(모노레포)로 둔다. 서버 배포(`deploy-remote.sh`·Dockerfile)는 `mobile/`을 무시하도록 `.dockerignore`에 추가한다. 앱 배포는 서버 배포와 **별개**다(앱 버전과 API 버전 호환을 `/api/v1`로 고정하고, 깨지는 변경은 `/v2`).

## 6. 빌드·배포·시험 — 사용자 손이 가는 것
| 단계 | 필요한 것 | 누가 |
|---|---|---|
| 개발 빌드 | 이 컨테이너에서 APK 생성(Android SDK 명령줄 도구 설치 → Gradle). 에뮬레이터는 못 돌리므로 **사용자 폰에 설치**해 본다("출처를 알 수 없는 앱" 허용 또는 `adb`) | Claude 빌드 → 사용자 설치·확인 |
| 서명 키 | 릴리스 서명 키(keystore)는 비밀값. 저장소·대화에 넣지 않고 사용자 PC 또는 Play 앱 서명에 보관 | 사용자 |
| 푸시 | Firebase 프로젝트 생성 → 안드로이드 앱 등록(패키지명 예: `kr.widebot.app`) → `google-services.json`(앱용)·서비스 계정 키(서버용) | 사용자 생성, Claude 설정 |
| 내부 배포 | ① APK 파일 직접 전달(직원용, 가장 단순) ② Google Play **내부 테스트** 트랙(최대 100명, 심사 가벼움) | 사용자 결정 |
| 정식 출시 | Google Play 개발자 계정(1회 등록비, 최신 조건은 확인), 개인정보처리방침 URL(웹에 페이지 추가), 앱 심사. 고객사 배포 시 필요 | 사용자 |
| 시험 | 서버: vitest에 API 시험 추가(타 사업장 차단·고객 명령 차단·멱등 키·토큰 만료·기기 끊기). 앱: 핵심 화면 스냅샷 시험 + 사용자 폰 실기 | Claude + 사용자 |

## 7. 단계 계획(제안)
| 단계 | 내용 | 완료 기준 | 기간 감 |
|---|---|---|---|
| **0. 서버 API·푸시** | `/api/v1` 라우트, Bearer 세션(기기 목록), `push_devices`, 알림 PUSH 채널, FCM 발송(설정 없으면 모의) | API 시험 통과, 웹 동작 변화 없음, 배포 | 1주 |
| **1. 앱 뼈대** | 로그인, 홈, 사업장·로봇 조회, 장애 목록·조치, 푸시 수신·딥링크, 알림함 | 사용자 폰에 APK 설치, 샘플·실서버 모두 확인, 장애 푸시 실수신 | 1~2주 |
| **2. 조작·편의** | 로봇 명령(확인 대화상자·멱등 키·결과 추적), 보고서 PDF, 내 구독·기기 관리, 생체인증 잠금, 조치 사진 | 명령 실기는 웹과 같은 조건(사용자 허락·충전 중·지정 로봇)에서만 | 1~2주 |
| **3. 배포** | 아이콘·스토어 문구·개인정보처리방침, 내부 테스트 → (고객사 필요 시) 정식 출시 | 스토어 등록 | 사용자 일정 |
| 4. iOS | 같은 코드로 iOS 빌드(Apple 개발자 계정·Mac 또는 EAS 빌드) | — | 별도 |

0단계는 **Web Push를 택해도** 거의 그대로 쓰인다(FCM 대신 VAPID 발송만 다름).

## 8. 보안·운영 규칙(앱에 적용)
- HTTPS만(cleartext 금지), 서버 주소는 앱 설정에 고정(`https://widebot.kro.kr`), 개발용 주소 전환은 개발 빌드에만.
- 토큰은 암호 저장소, 로그아웃·기기 끊기·사용자 비활성화 시 서버에서 즉시 무효. 앱 삭제 시 푸시 토큰은 FCM 무효 응답으로 정리.
- 앱 안에 비밀값 없음(Firebase 앱 설정은 공개 가능 값). PUDU 키·DB 등은 지금처럼 서버에만.
- 고객 계정에 원시 오류·내부 메모·초안 비노출 — 서버 응답에서 이미 걸러지므로 앱은 받은 것만 보여 준다. 알림창 문구도 요약만.
- 명령 감사 기록에 `channel: app`·기기 이름을 남긴다(누가 어느 폰에서 보냈는지).
- 앱 로그 수집(크래시 리포트)을 넣는다면 개인정보처리방침에 적고, 화면 데이터는 보내지 않는다.
