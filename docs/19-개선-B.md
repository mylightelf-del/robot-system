## 1. B7 청소 범위 증빙 — "PUDU 실적엔 구역 정보가 없다"는 틀렸다
- 실기 확인(2026-11-07): 청소 보고서 **상세**(`/data-board/v1/log/clean_task/query`)의 `floor_list`(JSON 문자열)에 다음이 있다. 목록 API 에는 없어서 그동안 못 봤다.
  - `area_array[]`: 작업에 포함된 구역(`area_id`, `area_name`, `clean_count`(이번 작업에서 청소한 횟수), `area`(㎡))
  - `task_result_url`: PUDU 가 만든 **결과 지도 PNG**(지도 위에 청소한 범위를 초록으로 칠한 그림, 공개 S3, 15KB 안팎)
  - `rubbish_distribution_url`: 쓰레기 분포 히트맵 PNG
  - 상세의 `percentage`: 작업 수행률(%)
- 구현
  - 실적(`actual_runs.coverage`)에 수행률·구역별 청소 횟수·이미지 URL 을 저장하고, 청소한 구역(`clean_count>0`)을 이 시스템 구역과 **제조사 구역 ID(`zones.vendor_zone_id`) 우선, 없으면 이름**으로 맞춰 `zoneIds` 를 채운다. 지도 가져오기가 이제 구역의 제조사 ID 를 저장한다(기존 구역은 이름으로 맞춰진다).
  - 결과 지도 이미지는 새 실적마다 서버가 받아 **DB 에 보관**(`run_images`, 제조사 보관 기간과 무관). 화면: 로봇 상세 실적 표 『결과 지도』, 일간·설치 보고서 작업 목록 『결과 지도』(`/api/runs/<id>/image`, 로봇 접근 권한).
  - 보고서: 구역별 실적 표가 다시 나오고(이전엔 구역 정보가 없다고 뺐음), 작업 목록에 **수행률**, 요약에 **평균 작업 수행률**(PPT 완료율 카드 비고·Excel 요약).
  - 과거 실적: `scripts/recompute-coverage.ts [--images N일]` 로 raw_payload 에서 다시 파싱(멱등). 운영 반영은 3장.
- 한계: 궤적(선)은 없고 PUDU 가 그린 결과 그림과 구역별 횟수만 있다. 히트맵은 저장하지 않고 URL 만 둔다(필요하면 `?kind=heatmap`).

## 4. 운영에서 할 일
- 알림 수신 설정에서 '소모품·점검' 종류를 받을 수신자를 켠다(기존 수신자는 꺼져 있음).
- 외부 시스템 연동이 필요하면 관리 설정에서 토큰을 발급해 전달한다(사업장 범위 지정 권장). 토큰 유출 시 즉시 폐기.
- 구역별 표가 비어 있는 층은 고급 설정에서 『PUDU 지도 가져오기』로 구역 ID 를 맞추면 정확해진다(이름이 같으면 가져오기 없이도 맞는다).

## 6. B8(화면에서 예약 만들기·바꾸기)을 하지 않은 이유
- PUDU Cloud API 에 **예약 생성·수정 API 가 없다**(`cron/list` 읽기와 `task/exec` type 10 '예약 on/off' 뿐, `docs/06` 4장). 생성은 PUDU 앱에서만 가능.
- type 10 의 본문 규격(켜기/끄기 값)이 문서에서 확인되지 않았고, 실제 로봇 명령 시험은 사용자 지시로 중지 상태다. 추측 구현은 하지 않는다.
- 다음 단계 제안: 대리점에 type 10 본문 예시를 받고, 시험 허용 시 충전 중인 로봇으로 on/off 1회 확인 뒤 화면에 '예약 켜기/끄기'만 붙인다. 생성·시간 변경은 PUDU 앱 안내로 둔다.
