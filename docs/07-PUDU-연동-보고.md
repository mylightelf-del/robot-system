# 07. PUDU Cloud API 연동 — 구현·시험 보고

기준: `docs/06-PUDU-API-검토.md`(공식 문서 검토)와 인수인계 문서 9장. 사용자 결정에 따라 CenoBots 보다 PUDU 를 먼저 연동했다.

> 1차 시험은 공식 문서 규격의 **모의 PUDU 서버**(`tests/pudu-mock-server.ts`)로 했고, 이어서 **발급 키로 실서버에 읽기 전용 호출**을 해 응답 구조를 확인하고 차이를 반영했다(3-3절, `docs/06` 9장). 실제 로봇에 **명령은 아직 보내지 않았다**.

## 2. 설계에서 지킨 원칙 (인수인계 문서 기준)

- **주소·요청·응답을 추측하지 않음**: 모든 endpoint·필드·상태 코드는 공식 문서 페이지에서 확인한 것만 썼다(06 문서 4~6장). 문서에 없는 product_code 는 등록을 보류한다(화면에 "문서에 없는 코드(보류)").
- **키는 서버 환경변수에만**: 화면에서 키를 입력하지 않는다. 관리 화면은 "설정됨/없음" 만 보여 준다.
- **명령은 접수와 실행을 구분**: HTTP SUCCESS 는 "접수(ACCEPTED)" 일 뿐이며, 상세 조회(폴링)나 콜백(notifyCleanStatus)으로 로봇 상태가 바뀐 것을 본 뒤에야 EXECUTING/COMPLETED 로 올린다. 접수 후 설정 시간(기본값은 운영 설정의 접수 타임아웃)까지 변화가 없으면 "결과 불명(UNKNOWN)" 으로 둔다.
- **중단(STOP)**: 청소 중이면 일시정지(status 3) 후 취소(status 4) 두 번 호출한다. 문서에 "청소 중 바로 취소 가능" 여부가 명시되지 않아 안전한 순서를 택했다(실기에서 확인).
- **고객 비공개**: 원시 상태·제조사 ID·vendorMeta(매장 ID·MAC)·내부 메모·통신 로그는 고객 역할에 내려주지 않는다.
- **감사**: 연결 확인·로봇 등록·동기화 실행·명령 전송은 모두 감사 이력에 남고, 제조사 trace_id 를 함께 저장한다.
- **콜백은 보조**: 콜백 누락·지연이 있어도 폴링이 상태·보고서·장애를 채운다. 반대로 콜백이 먼저 와도 폴링이 과거 데이터로 덮어쓰지 않도록 데이터 시각(dataAt)을 비교한다.

### 3-3. 실서버 확인 (2026-10-28, 읽기 전용)
사용자가 전달한 키로 `sea` 클러스터에 접속했다. 인증은 첫 호출부터 통과했다. 확인 과정과 결과:
1. `npm run pudu:check -- --shops 포스코와이드` 로 매장 6곳을 찾고, 로봇 목록에서 청소로봇이 있는 4곳(선릉센터 CC1Pro 3대, 포스코이앤씨 단기 MT1 3대, 성남분당 MT1 1대, 광양포항POC CC1 2대)을 `PUDU_SHOP_IDS` 로 지정했다.
2. 개발 DB 에 9대를 등록하고 동기화 4종을 실행: 상태 9/9 갱신, 등록 작업 188·예약 34·소모품 49, 최근 7일 보고서 67건 → 실적 67건, 장애 로그 23건 → 장애 21건(중복 2건 제외). 이후 워커를 띄워 30초 폴링이 반복 성공하는 것을 확인했다.
3. 화면: 관리 설정(허용 매장·로봇 조회·등록), 로봇 상세(실제 상태 "충전 중 100%", 소모품 잔여 수명 76~100%, 7일 실적 30건, 장애 2건), 장애·조치, 대시보드가 실제 데이터로 렌더링되고 콘솔 오류가 없다. 스크린샷 `docs/screenshots/25~29`.
4. 문서와 다른 응답은 모두 코드에 반영했다(`docs/06` 9장 표). 특히 다음 둘은 설계에 영향이 커서 따로 적는다.
   - **키의 범위**: 대리점 전체 키라 다른 고객사의 매장 4,154곳·로봇 6,724대가 보인다. 허용 매장(`PUDU_SHOP_IDS`) 없이는 live 가 켜지지 않게 했고, 조회·등록·보고서·장애 동기화를 허용 매장 안으로 제한했다. 관리 화면도 허용 매장 밖 로봇은 보여 주지 않는다.
   - **통계 API 는 `sn` 을 무시**하고 `shop_id` 로만 걸러진다. 로봇별이 아니라 매장별로 조회한 뒤 등록 로봇의 SN 만 적재한다.
5. 실기에서 드러나 고친 문제: 과거 장애 로그를 적재하면서 정상(충전 중) 로봇을 ERROR 로 표시하던 것 → 로그 동기화는 현재 상태를 건드리지 않고, 실시간 콜백만 상태를 바꾸게 했다. 값이 없는 쿼리 키를 키만 보내면 서버가 빈 값 필터로 해석해 0건이 되는 문제 → 보내지 않게 했다.

### 3-5. 시험 중 발견해 고친 문제(모의 서버 단계)
1. **콜백 URL 이 로그인으로 리다이렉트됨** — 인증 프록시가 `/api/webhooks/*` 를 공개 경로로 두지 않아 PUDU 서버가 307 을 받게 되어 있었다. 단위 시험은 저장 함수만 직접 호출해 이를 놓쳤다. 프록시 예외를 추가하고 라우트·프록시를 함께 부르는 시험(15번)을 더했다.
2. **live 모드에서 샘플 로봇도 실서버에 조회** — 샘플 적재 PUDU 로봇 15대(가상 SN)가 폴링 대상에 들어가 실서버에 의미 없는 요청을 보내고, 시뮬레이션 틱이 실제 로봇의 상태를 덮을 수 있었다. `vendorMeta.source="api"` 로 실제 로봇을 구분해 폴링·명령·시뮬레이션을 분리했다(시험 7번).
3. 로봇 화면이 실제 로봇에도 "시뮬레이션 시나리오" 선택과 유지관리 "샘플" 표시를 보여줬다 → 실제 로봇에서는 숨기고 "실제 로봇에 전송됩니다" / "API" 로 바꿨다.
