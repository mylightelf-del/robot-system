# 03. 2단계 기술 선택 — DB 비교와 클라우드 구성안

작성일: 2026-10-28 · 전제: 5개 사업장 · 20대 · 사용자 수십 명 · 외부 클라우드 · PC·모바일 웹
가격은 조회 없이 단정하지 않는다. 공급사 후보가 정해지면 당시 가격표를 조회해 월 예상 비용을 따로 제시한다.

## 1. 데이터 규모 가늠 (설계 근거)
- 로봇 상태 수신: 20대 × 1분 주기 = 하루 약 2.9만 건. 원시 상태를 전부 보관하면 월 약 86만 행. → 최신 상태는 1행/로봇으로 갱신하고, 이력은 요약(5분 단위) 또는 보관기간(예: 90일)으로 제한하는 설계가 필요하다. 보관기간은 운영 설정값.
- 실제 작업(실적): 20대 × 하루 1~3건 = 월 1~2천 행. 작다.
- 장애·명령·감사 기록: 월 수천 행.
- 결론: 데이터양은 작고, 중요한 것은 **정합성(중복 제거·스냅샷)·집계(보고서)·백업**이다. 어떤 관계형 DB든 성능은 문제 없고, 운영 편의와 관리형 서비스 유무가 기준이 된다.

## 2. DB 비교

| 후보 | 장점 | 단점 | 이 프로젝트 적합도 |
|---|---|---|---|
| **PostgreSQL** | 트랜잭션·제약조건으로 중복/정합성 보장 쉬움. JSONB 로 제조사 원시 상태·Webhook 원문 보관. 시간대 타입(timestamptz) 내장. 집계·윈도우 함수 강함. 관리형 서비스 폭이 가장 넓음(AWS RDS/Aurora, 네이버클라우드 Cloud DB for PostgreSQL, Supabase, Neon 등). | 운영자가 MySQL 에 익숙하면 학습 필요. | **높음** |
| MySQL / MariaDB | 국내 친숙도 높음, 관리형 많음. | JSON·시간대·집계 기능이 PostgreSQL 보다 약함. 보고서 집계 SQL 이 길어짐. | 중간 |
| SQLite | 설치 없음, 파일 하나. | 단일 서버 파일이라 클라우드 다중 인스턴스·관리형 백업·동시 쓰기에 부적합. | 낮음(로컬 실험용으로만) |
| NoSQL (DynamoDB, MongoDB 등) | 유연한 스키마, 대량 이벤트 적재. | 보고서처럼 조인·집계가 많은 업무에 불리. 정합성(중복 제거·스냅샷)을 앱에서 다 처리해야 함. | 낮음 |

**선택: PostgreSQL 16.** 근거는 (1) 정합성 규칙(중복 키, 확정 스냅샷, 배치 이력)을 DB 제약으로 강제할 수 있고, (2) 제조사별 원시 데이터를 JSONB 로 그대로 보관하며, (3) UTC 저장·사업장 시간대 표시 요구를 timestamptz 로 자연스럽게 처리하고, (4) 어느 클라우드를 고르더라도 관리형 PostgreSQL 이 있어 공급사 종속이 작기 때문이다. 이 개발 환경에도 PostgreSQL 16 이 있어 2단계에서 실제 DB 로 개발·테스트한다.

ORM/마이그레이션: **Prisma** 를 제안한다. 스키마 파일 하나로 DB 변경 이력(마이그레이션)을 git 에 남기고, TypeScript 타입이 자동 생성되어 초보자가 읽기 쉽다. 대안 Drizzle 은 SQL 에 가깝고 가볍지만 학습 곡선이 있다.

## 3. 클라우드 구성안 (DB·앱 모두 클라우드)

구성 요소의 책임(인수인계 10장): ① 웹 앱 서버 ② DB ③ 백그라운드 워커(상태 주기 조회·Webhook 수신 후속 처리·예약 실행기·알림 발송) ④ 보고서 PDF 저장(파일 저장소) ⑤ 알림 모듈.

| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **A. 관리형 조합** | 앱: Vercel 등 서버리스 / DB: Supabase·Neon 등 관리형 PostgreSQL | 배포·운영 손이 가장 적음. 자동 HTTPS·스케일. | 서버리스는 상시 실행되는 워커(주기 조회·예약 실행기)가 없어 별도 Cron/Queue 서비스를 붙여야 함 → 구성 요소가 늘어 초보 운영자에게 오히려 복잡. 리전·데이터 위치 확인 필요. |
| **B. VM 1대 + 관리형 DB** | 앱+워커: 클라우드 VM 1대에 Docker Compose(웹·워커·리버스프록시) / DB: 같은 클라우드의 관리형 PostgreSQL / 파일: 오브젝트 스토리지 | 구조가 단순해 이해·장애 추적이 쉬움. 워커가 상시 실행되어 Webhook·주기 조회·예약에 자연스러움. 비용 예측이 쉬움. DB 백업·패치는 관리형이 맡음. | VM 의 OS 패치·모니터링·재시작은 직접(또는 간단한 자동화). 트래픽 급증 대응은 수동 증설(이 규모에서는 문제 아님). |
| C. 관리형 컨테이너 + 관리형 DB | AWS ECS Fargate/App Runner 등 + RDS | 운영 부담과 확장의 균형. | 설정 항목이 많아 초기 난이도 높음. 20대 규모에는 과함. |

**추천: B안.** 20대 규모와 "단순한 서버 구조 우선" 원칙에 가장 맞고, 백그라운드 수집·예약·Webhook 처리를 한 곳에서 운영할 수 있다. 앱은 Docker 이미지로 만들어 두므로 나중에 C안(관리형 컨테이너)으로 옮기기 쉽다. A안은 규모가 더 작거나 워커가 필요 없을 때 적합하다.

데이터 위치: 고객사 사업장 데이터이므로 **한국 리전**을 기본으로 한다.

공급사 후보(한국 리전 보유):
- **AWS (서울)**: 문서·사례 가장 많음. EC2 + RDS for PostgreSQL + S3.
- **네이버클라우드(NCP)**: 국내 청구·지원, 공공·국내 기업 친숙. Server + Cloud DB for PostgreSQL + Object Storage.
- (A안 대안) Vercel + Supabase(서울 리전): 워커는 별도 필요.

최종 공급사는 운영 담당자 선호(기존 계정·청구 체계·지원 언어)에 따라 정한다. 정해지면 당시 가격을 조회해 월 예상 비용(최소 구성)을 제시한다.

## 3-A. 추가 검토: Oracle Cloud · Cloudflare · Google Cloud (2026-10-28 운영 담당자 질문)

같은 기준(B안: VM 1대 + 관리형 PostgreSQL + 파일 저장소, 한국 리전, 상시 워커)으로 비교했다. 가격은 공개 블로그·요약 기준이므로 계약 전 공식 가격표로 재확인한다.

| 공급사 | 한국 리전 | 관리형 PostgreSQL | VM/워커 | 장점 | 주의점 | B안 적합도 |
|---|---|---|---|---|---|---|
| **Google Cloud** | 서울(asia-northeast3, 3개 존) | Cloud SQL for PostgreSQL | Compute Engine(또는 Cloud Run) + Cloud Storage | AWS 와 동급 구성. 문서·콘솔 한국어 양호. Google Workspace 를 쓰는 회사면 계정 관리가 편함 | 무료 등급(e2-micro)은 미국 리전 한정이라 서울은 처음부터 과금. | **높음** (AWS 와 동급 대안) |
| **Oracle Cloud(OCI)** | 서울(South Korea Central) · 춘천(South Korea North, 확인 필요) | OCI Database with PostgreSQL(유료) | Always Free VM(ARM 2 OCPU/12GB 수준으로 축소 보고, AMD 소형 2대) + Object Storage | 상시 무료 자원이 있어 **비용 최소화에 유리**. 유료 구성도 저렴한 편 | 무료 Autonomous DB 는 Oracle DB 이지 PostgreSQL 이 아님. 서울 리전은 무료 ARM VM 생성이 어렵다는 보고가 있고, 유휴 자원 회수 규정이 있어 **고객 대상 운영 시스템을 무료 등급에 의존하면 안 됨**(유료 구성으로 봐야 함). 국내 사례·문서가 AWS/GCP 보다 적음 | 중간 (유료 구성이면 가능) |
| **Cloudflare** | 전 세계 엣지(리전 선택 개념 없음) | 없음 (D1 은 SQLite, Hyperdrive 는 외부 PostgreSQL 로의 연결 가속) | 전통적 VM 없음. Workers(서버리스) + Cron Triggers, 컨테이너는 제한적 | CDN·DNS·WAF·DDoS 방어가 강함. 정적/경량 앱 배포가 쉬움 | Next.js 는 OpenNext/vinext 어댑터를 거쳐야 하고 공식 권장 경로가 바뀌는 중. DB 연결이 요청 단위로 제한되고 상시 워커(주기 조회·예약 실행기)를 두기 어려움. DB 는 결국 다른 곳에 둬야 함 | 낮음 (단독 호스트로는 부적합, **앞단 DNS/보안 계층으로는 좋음**) |

정리:
- **Google Cloud** 는 AWS 와 같은 수준으로 B안을 그대로 구성할 수 있다. AWS 대신 선택해도 코드·구성 변경이 없다.
- **Oracle** 은 비용을 가장 낮출 수 있지만, 무료 등급은 시험용으로만 보고 운영은 유료 구성으로 계획해야 한다. 그 조건이면 가능하다.
- **Cloudflare** 는 주 호스트가 아니라 **도메인·HTTPS·방화벽 앞단**으로 함께 쓰는 것을 제안한다(어느 공급사를 고르든 조합 가능).

## 3-C. 무료 플랜 재검토 (2026-10-28, "가볍게 쓸 것이므로 무료 플랜으로")

전제: 20대·사용자 수십 명·하루 수만 건의 상태 수신은 무료 플랜 범위 안에 든다. 단, 무료 플랜은 **SLA·백업·지원이 없고 조건이 자주 바뀌므로** (1) 코드는 공급사에 묶이지 않게(Docker + PostgreSQL) 만들고, (2) 유료 전환 경로를 미리 둔다. 아래 수치는 공개 요약·블로그 기준이며 계약 시 공식 페이지로 재확인한다.

| 안 | 구성 | 비용 | 장점 | 주의점·대응 |
|---|---|---|---|---|
| **F1. Oracle Always Free VM (서울) + Docker + Cloudflare** | VM 1대(ARM A1 또는 AMD 소형)에 Docker Compose: 웹·워커·PostgreSQL. 백업은 OCI Object Storage(무료 범위). 앞단 Cloudflare 무료(DNS·HTTPS·방화벽) | 0원 | 한국 리전. 상시 워커(주기 조회·예약·Webhook)가 자연스러움. 구조가 단순하고 나중에 어떤 VM 으로든 그대로 이전 가능 | ① **유휴 회수**: 7일간 CPU 사용 95퍼센타일이 약 20% 미만이면 회수될 수 있음(출처별 10~20%, 공식 문서 재확인). 커뮤니티는 계정을 종량제(PAYG)로 전환하면 회수 대상에서 빠진다고 하나 공식 확인 필요 → PAYG 전환 + 예산 알림 0원 설정 제안. ② 서울 리전 ARM 무료 VM 생성이 어려울 수 있음 → AMD 소형 2대(앱/DB 분리) 대안. ③ 무료 할당이 축소된 보고(ARM 2 OCPU/12GB)가 있음. ④ 백업·패치는 직접(일일 DB 덤프 자동화 스크립트 제공) |

Cloudflare Workers + Supabase 무료 + Cloudflare Cron** | 앱: Workers(무료 10만 요청/일) / DB: Supabase 무료(서울 리전, PostgreSQL 500MB) / 주기 조회: Cron Triggers / Webhook: Workers 엔드포인트 | 0원 | 서버 관리 없음. 한국 리전 DB | ① Supabase 무료 프로젝트는 **7일 저활동 시 일시정지**(유료는 안 함) → 주기 조회가 DB 를 계속 쓰면 유지되나 보장은 아님. ② Next.js 16 을 Workers 에 올리는 어댑터(OpenNext/vinext)가 변동 중, 요청당 CPU 시간 짧음, DB 연결은 요청 단위 → PDF 생성·긴 처리에 불리. ③ 500MB 한도 → 상태 이력 보관기간 제한 필요 |
| F3. Render/Railway/Koyeb 류 무료 | 웹 서비스 + 무료 Postgres | 0원 | 설정 쉬움 | 무료 웹은 15분 유휴 시 중지(첫 접속 느림), 무료 DB 는 만료형 트라이얼이 많음. 한국 리전 없음 |
| 제외: Vercel Hobby | — | 0원 | Next.js 최적 | **상업적 사용 금지** 약관 → 회사 운영 시스템에 부적합 |
| 제외: Google/AWS 무료 | — | — | — | Google 무료 VM 은 미국 리전 한정, AWS 는 기간·크레딧 한정 → 한국 리전 상시 무료 불가 |

**추천: F1.** "가볍게·무료·한국 리전·상시 워커" 네 조건을 동시에 만족하는 유일한 안이다. 조건: PAYG 전환(무료 한도 안에서는 0원) + 예산 알림, 일일 백업 자동화, Cloudflare 앞단. ARM VM 을 서울에서 못 만들면 AMD 소형 2대로 시작한다. 트래픽·데이터가 커지면 같은 Docker Compose 를 유료 VM + 관리형 PostgreSQL(B안)로 옮긴다.
**대안: F2** — VM 을 전혀 관리하고 싶지 않을 때. 단 Workers 어댑터 호환성을 2단계 끝에서 실제로 시험한 뒤 결정한다.

개발 진행에는 영향 없음: 2단계는 어느 안이든 공통인 Docker 이미지 + PostgreSQL + 상시 워커로 만든다. F2 를 택하면 워커를 Cron Trigger 호출형으로 바꾸는 작은 작업이 추가된다.

## 3-D. AWS 를 서버로 쓰는 경우 (2026-10-28 추가 비교)

AWS 는 2025-07-15 이후 신규 계정의 무료 방식이 바뀌었다. 상시 무료 VM 이 없고 **크레딧($100, 온보딩 활동으로 최대 $200)** 을 주며, 무료 플랜은 6개월 또는 크레딧 소진 시 계정이 닫히고, 유료 플랜은 크레딧 소진 후 종량제로 넘어간다. 따라서 AWS 는 "무료"가 아니라 **"처음 몇 달 무료, 이후 소액 유료"** 로 봐야 한다. (공개 요약 기준, 공식 페이지 재확인 필요)

AWS 안에서 가벼운 운영에 맞는 선택지:
| AWS 구성 | 월 비용(공개 요약, 서울) | 장점 | 주의점 |
|---|---|---|---|
| **AWS-1. Lightsail VM 1대 + Docker** (웹·워커·PostgreSQL 같이) | IPv4 포함 $5(0.5GB)부터, Docker 3개를 올리려면 2GB 급(약 $12) 권장. 스냅샷 백업 소액 추가 | AWS 중 가장 단순. 고정 요금이라 예측 쉬움. 서울 리전. 나중에 EC2/RDS 로 승격 가능 | 무료 아님(크레딧 소진 후 과금). 백업·패치는 직접(F1 과 동일) |
| AWS-2. Lightsail VM + Lightsail 관리형 DB | VM 약 $12 + DB $15부터 | DB 백업·패치를 AWS 가 맡음 | 월 $27 안팎. 가벼운 용도엔 과함 |
| AWS-3. EC2 + RDS + S3 (B안) | 구성에 따라 $30~ | 정식 구성, 확장·보안 옵션 풍부 | 설정 항목이 많아 초보 운영자에게 난이도 높음 |

**F1(Oracle 무료) 대 AWS-1(Lightsail) 비교**
| | F1 Oracle 무료 VM | AWS-1 Lightsail |
|---|---|---|
| 비용 | 0원 (PAYG 전환해도 무료 한도 내 0원) | 처음은 크레딧으로 0원, 이후 약 $12/월 |
| 한국 리전 | 서울 | 서울 |
| 구조 | 동일 (Docker: 웹·워커·PostgreSQL) | 동일 |

| 운영 난이도 | 중간 | 중간 (콘솔이 더 단순) |
| 확장 경로 | 유료 VM 으로 이전 | 같은 계정에서 EC2/RDS 로 승격 |

정리: **구조는 완전히 같고, 차이는 "0원이지만 회수 규정·지원 없음(Oracle)" 대 "월 $12 안팎이지만 안정적(AWS Lightsail)"** 이다. 고객사에 보여 주는 운영 시스템이라면 월 $12 수준의 AWS Lightsail 이 "가볍게 쓰되 끊기지 않게" 에 더 맞고, 비용을 0원으로 못 박아야 한다면 Oracle 이다. 어느 쪽이든 Docker Compose 한 벌로 배포하므로 **지금 결정하지 않아도 2단계 개발은 진행할 수 있다.**

## 3-E. 확정: 호스팅 (2026-10-28 결정)
**AWS Lightsail(서울) 서버 1대 + Docker Compose(웹·워커·PostgreSQL) + Cloudflare 앞단(DNS·HTTPS·방화벽).**
- 처음에는 2GB급 인스턴스(월 약 $12, 공식 가격 재확인) + 자동 스냅샷. 커지면 같은 계정에서 EC2/RDS 로 승격.
- 코드·배포 구성은 공급사에 묶이지 않게 유지(Docker + PostgreSQL). 배포 절차는 `docs/05-배포-운영-가이드.md`.

ORM 변경 메모: 2장에서 Prisma 를 제안했으나 구현 시점에 Prisma 주요 버전 전환(엔진 교체·드라이버 어댑터 필수)으로 설정이 복잡해져 **Drizzle ORM + drizzle-kit** 으로 구현한다. 근거: 마이그레이션이 일반 SQL 파일로 생성되어 git 에서 읽고 검토하기 쉽고, 런타임 코드 생성 단계가 없어 Docker 빌드가 단순하다. 스키마는 TypeScript 파일 하나(`src/lib/db/schema.ts`)에 있다.

## 3-B. 확정: 인증 방식
**이메일 + 비밀번호, 초대 링크 방식** (2026-10-28 결정). 본사 관리자가 사용자를 등록하면 초대 링크로 비밀번호를 설정한다. 고객사 사용자도 같은 방식. 2단계 인증·SSO 는 추후 검토.

## 4. 2단계 범위 (이 선택을 전제로)
1. PostgreSQL 스키마 + Prisma 마이그레이션(DB 변경 이력 git 관리). 메모리 저장소를 리포지토리 계층으로 교체. 샘플 데이터는 seed 스크립트로 유지.
2. 실제 인증: 이메일+비밀번호(초대 링크로 최초 설정), 서버 세션, 만료, 비활성화 즉시 차단. 인가 규칙은 1단계 `authz.ts` 유지.
3. 감사 이력 DB 저장, 환경 분리(dev/staging/prod)와 비밀값은 환경변수.
4. Docker 이미지 + docker-compose(로컬·VM 공용), 백업·복구 절차 문서, 키 교체 절차, 운영 감시 항목.
5. 1단계 테스트 전부를 DB 기반으로 재실행 + 인증 테스트 추가.
